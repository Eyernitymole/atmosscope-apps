# AtmosScope v1.6 综合会商接线与发布设计

日期：2026-09-19

状态：待用户审阅

目标分支：`agent/v1.6-consultation`（PR #12）

## 1. 目标与已知现状

用户选择方案 A：在现有专业图集页面内提供真实可用的综合会商，组合 500 hPa 位势高度、850 hPa 水汽输送和未来 24 小时降水，给出保守的规则式文字意见。成功标准是按钮可操作、产品可解释、缺测不造数、原有图集不回退，随后才合并 PR #12 并发布 v1.6.0 的 APK、Windows 安装包和校验文件。

当前 PR 的 CI 已通过，但 `web/index.html` 中的 `data-moisture="consultationComposite"` 尚未进入 `web/moisture.mjs` 的 `loaders`；点击会调用不存在的函数。`consultation.mjs`、`consultation-controller.mjs`、`consultation-summary.mjs`、`consultation-renderer.mjs` 已有部分能力，但缺少完整的数据—诊断—界面链路。`.release-version` 与 `package.json` 均仍为 `1.5.0`。因此 CI 通过不等于可发布。

## 2. 范围与边界

本次只接通现有“综合会商”入口，并完成 v1.6.0 发布收尾。保留天气雷达、模式云场、降水、探空、动力、水汽通量和垂直剖面等现有入口、控件和事件绑定。不换数据源，不重构整站，不训练 AI，不新增官方预警级别，不把粗采样图解释为原始全分辨率模式产品，不编造台风或雷达信息。已有兼容文件可留在仓库，但页面不再单独加载补丁脚本。

普通天气入口彻底脱离 ChatGPT Site 属于后续阶段，不纳入 v1.6 发布条件。版本发布不以仅看见绿色 Actions 作为验收：必须检查实际安装资产及校验值。

## 3. 组件职责与数据流

1. `web/moisture.mjs` 负责响应 `.moisture-tab`、模式/时效/刷新控件，调用现有 `request()`，显示加载状态，并将会商产品注册到 `loaders`。保留原有水汽和剖面逻辑，不复制一套网络入口。
2. 新的纯数据转换单元 `web/consultation-data.mjs` 接收 Open-Meteo 返回的逐点 `hourly` 数据、网格坐标和选中时效；校验时间窗口及字段，生成 500 hPa 高度、850 hPa 温湿风、未来 24 小时累计降水的有效矩阵与有效时间。返回明确的成功或缺测结果，不接触 DOM 或地图。`moisture.mjs` 复用原有 `qMatrix()`、`fluxComponents()` 推导 `q·u/q·v`，再交给现有 `consultationComposite(fields)` 组装，避免复制比湿公式或循环导入带 DOM 副作用的模块。
3. `web/consultation-summary.mjs` 仅依据通过校验的派生字段生成保守的规则意见；`web/consultation-controller.mjs` 将其作为规则引擎输入，负责与现有 panel/fallback 接口对齐，避免两个互不相干的 `diagnoseConsultation()` 实现。区域最大降水只标为“采样网格区域最大值”，不自动判断低槽位置或作官方预警。
4. `moisture.mjs` 复用现有 `draw()` 绘制 24 小时降水填色；`web/consultation-renderer.mjs` 负责 500 hPa 位势高度等值线与 850 hPa 水汽输送稀疏矢量 Leaflet 图层，复用 `web/meteo.mjs` 已有的 `contourSegments()`。`moisture.mjs` 统一管理这些图层的生命周期，切换产品时移除旧图层，避免叠影。
5. 侧栏展示数据源、所选模式、预报起止时刻、图例、派生量说明和规则会商意见。用户切换模式、时效或刷新时，重新获取对应数据并更新所有图层与说明；不能保留上一模式的旧结论。

## 4. 数据契约与缺测规则

- 与当前模式选择和预报时效一致，一次请求 `geopotential_height_500hPa`、`temperature_850hPa`、`relative_humidity_850hPa`、`wind_speed_850hPa`、`wind_direction_850hPa`、`precipitation`，沿用现有 9×11 采样网格、73 小时响应和 Open-Meteo 模式端点。
- “未来 24 小时累计降水”定义为从所选 `hourly.time[index]` 起连续 24 个逐小时降水值之和，而非过去 24 小时。所选时效后不足 24 项时，不计算或标称为完整的 24 小时量；控件可继续选该时效，但会商页明确显示“完整 24 小时预报时段不足”。零降水 `0` 是有效值，`null`、缺项、非有限数不是零。
- 整个必需字段缺失、响应点数与坐标不一致或完整 24 小时窗口缺失时，返回列明原因的“数据不足”，不以零代替，不输出完整组合图或风险结论。若只有部分网格点缺测，有效单元可绘制，侧栏写明有效点数/总点数，最大值只称“有效采样点最大值”；不得对缺测区域插值或给出区域风险等级。若有效网格不足以构成填色单元，地图不绘制该层并显示“数据不足”。
- 比湿和 `q·u/q·v` 沿用 v1.5 已验证的 850 hPa 公式；输出和图例注明这是采样网格派生诊断。绘制矢量时 `u` 向东、`v` 向北，屏幕箭头旋转角需处理屏幕 y 轴向下的方向差异；测试覆盖纯北风对应箭头朝上。
- 高度等值线只来自真实有效的高度矩阵，按范围内每 60 m 一级绘制；没有足够有效数据则不绘线。`trailingPrecipitation()` 只在数据单元确认 24 项均有效后调用，不能依靠它当前的缺测转零行为。降水填色使用累计毫米数，侧栏明确当前 24 小时窗口。不同量纲不共用一个图例。
- 规则文字以可核验事实为主：完整网格下标明采样网格区域最大 24 小时降水、低层水汽输送图层可用性及 500 hPa 高度场可用性；局部缺测时只报告有效点事实和缺测比例。完整数据下以 10/30 mm 作内部关注筛查线时，必须写明不是官方暴雨预警标准；不从高度场极值直接推断槽脊或降水成因。没有完备的必需输入时只给“数据不足”和原因。

## 5. 异常、兼容与交互

网络失败、模式不支持、返回结构异常、缺少预报时刻或不足 24 小时，都在会商侧栏显示具体原因；不沿用上一次的图层与结论。会商加载器返回缺测状态时，顶部状态显示“数据不足”，不能被通用 `run()` 误写成“数据已更新”。快速切换模式/时效时，以请求序号只接受最新一次响应，防止旧请求覆盖新图。切换到原有天气产品时，恢复现有控件和地图显示行为。会商按钮保留 `.moisture-tab` 类和 `data-moisture` 标识，避免出现可见却无法加载的入口。

对组合产品的新增计算不改变 `moistureFlux850()`、`moistureFluxDivergence850()`、`verticalSection()` 的导出与现有测试契约。若真实数据源在某模式下不提供字段，界面应真实降级而非静默换模式。

## 6. 测试与发布门槛

1. 先写失败测试，再实现：覆盖完整 24 小时窗口、零降水、`null`/缺项、临界时效、错位点数、矢量方向、等值线有效单元、控制器缺测返回、按钮加载器接线与切换时清理旧图层。断言输出与状态，而不只搜索源文件关键词。
2. 运行整个 `npm test` 和 CI 的 JS 语法检查；保持此前 32 项及新增测试全绿。用可控数据对页面入口、模式/时效切换、侧栏结论与图层进行交互烟测；能访问真实气象 API 时再做一次真实取数检查，并区分 API 不可用与代码失败。
3. 上述功能验收后，把 `.release-version` 与 `package.json` 同时改为 `1.6.0`。合并前重新确认 PR head、CI、目标分支以及 `v1.6.0` tag 是否存在；若 tag 已存在，停止自动发布并单独处理冲突，不覆盖或删除既有发布。
4. 合并 PR #12 后确认 Release 工作流成功，并在 GitHub Releases 中实际检查 `AtmosScope-Android.apk`、`AtmosScope-Windows-Setup.exe`、`SHA256SUMS.txt` 三项；核对校验文件与两份资产一致。若签名、构建或上传失败，不宣称 v1.6.0 发布成功，并依据失败日志做针对性修复。

## 7. 不纳入本次的后续工作

更高分辨率模式产品、官方台风路径结构化接入、多模式同图比较、更多动力指标、普通天气站点独立化及现有长文件的大规模拆分，均待 v1.6 稳定发布后另行设计。
